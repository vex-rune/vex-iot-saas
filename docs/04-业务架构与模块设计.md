# 业务架构与模块设计

## 1. 业务范围

### 1.1 基础功能

- 登录 + JWT 权限控制
- 账号仅后台开通，无自助注册

### 1.2 管理功能（管理员）

- 设备管理：新增、编辑、删除、启用/禁用设备
- 点表管理：点位配置、公式配置、读写权限、批量导入导出
- 通知人管理：新增、编辑、删除通知人，配置短信/微信开关
- 报警管理：报警规则新增、编辑、删除、启停，阈值配置，关联通知人

### 1.3 操作功能（操作人员）

- 设备列表查看、在线状态查看
- 点表信息查看（只读）
- 点位实时数据监控
- 可读可写点位的远程控制下发
- 报警规则查看、报警历史记录查看
- 通知人列表查看

### 1.4 业务数据

- 用户账号信息（管理员、操作人员）
- 设备信息（PLC、网关）
- 点表配置（点位寄存器、公式、读写权限）
- 点位实时数据 + 历史时序数据
- 报警规则 + 报警记录
- 通知人信息

## 2. 后端模块划分（Maven 多模块）

| 模块 | 职责 |
|------|------|
| `common` | 通用工具、异常定义、统一响应封装、常量 |
| `security` | 登录鉴权、JWT 生成与校验、Spring Security 权限控制、角色定义 |
| `device` | 设备管理业务：设备 CRUD、在线状态、MQTT 接入配置 |
| `point-table` | 点表管理业务：点位 CRUD、公式配置、读写权限、批量导入导出 |
| `point-control` | 点位监控与控制：实时数据展示、控制指令下发、操作记录 |
| `alarm` | 报警管理业务：报警规则 CRUD、实时异常监测、报警记录、故障恢复 |
| `notify` | 通知人管理 + 消息通知：通知人 CRUD、短信/微信推送封装、通知重试 |
| `mqtt` | MQTT 通信模块：EMQX 连接管理、共享订阅消费、指令发布、断线重连、消息去重 |
| `archive` | 数据归档模块：定时任务执行冷数据快照导出、OSS 上传、归档日志、Mongo 过期集合清理 |
| `app-api` | 对外 REST 接口层（Nginx 反代目标），统一路由、参数校验、权限注解 |

**技术栈**：Java 17 + Spring Boot 3.x + Spring Security + Spring Data MongoDB + Eclipse Paho（MQTT 客户端）+ SpringDoc（API 文档）

### 3.2 前后端对接方式

- **业务请求**：REST `/api/*` 走 Nginx 反向代理到 SpringBoot 双实例
- **实时数据**：Java 侧订阅 MQTT 后，通过 SSE（Server-Sent Events）或 WebSocket 向前端推送点位实时数据更新
- **认证**：登录获取 JWT Token，后续请求 Header 携带 Token，后端无状态校验

### 3.3 前端部署

- 构建产物（`dist/`）放在 ECS-1 的 Nginx 静态目录
- Nginx 配置 SPA 路由回退（`try_files $uri $uri/ /index.html`）
- API 请求 `/api/*` 反向代理到 ECS-2 双实例

## 4. 数据存储策略

### 4.1 数据库选型

**MongoDB**，理由：
- 文档型存储，灵活适配点位异构数据结构（不同设备点表不同）
- 单集合无硬性行数上限，可存数十亿条时序数据
- 复合索引 + 范围查询满足工业时序数据查询需求
- 与 Spring Boot 生态集成成熟（Spring Data MongoDB）
- 技术栈统一，业务数据与时序数据同库，降低运维复杂度

### 4.2 数据存储模型

**核心设计：按设备存储原始数据包，不按点位拆分**

设备每次上报一个固定长度（500 字节）的原始数据包，各点位值通过指针偏移量从数据包中解析。历史数据按设备维度存储，每台设备 30 秒存一条记录，记录中包含完整的 500 字节原始数据包（MongoDB BinData 类型）。

**单条历史记录结构**：
- `_id`：MongoDB 自动生成
- `deviceId`：设备 ID
- `timestamp`：数据采集时间
- `rawData`：500 字节原始数据包（BinData）
- 点位值不单独存储，查询时由应用层按点表配置的指针偏移量从 rawData 中解析

**优势**：
1. 写入量按设备计而非按点位计，数据量降低 1-2 个数量级
2. 一条记录包含设备全部点位数据，查询无需聚合
3. 原始包完整保留，后续新增/修改点位解析规则无需改历史数据
4. 死区过滤：设备数据无变化时不新增记录，进一步减少写入量

### 4.3 数据量与磁盘计算

**基础参数**

| 指标 | 值 |
|------|-----|
| 设备数 | 80 台 |
| 每台点位 | 80 个（从 500 字节原始包解析） |
| 上报频率 | 30 秒/次 → 单台每天 2880 条 |
| 每日总条数 | 80 × 2880 = **230,400 条/天（23 万条）** |
| 每月总条数 | **约 691 万条/月** |
| 3 个月总条数 | **约 2074 万条** |

**单条记录磁盘占用**

| 组成部分 | 大小 |
|---------|------|
| 500 字节原始数据包（BinData） | 500 B |
| 元数据（_id + deviceId + timestamp + 字段名） | ~80 B |
| MongoDB 文档内部开销 | ~20 B |
| _id 索引 + (deviceId, timestamp) 复合索引 | ~50 B |
| **单条合计** | **~650 B** |

**无死区过滤（理论最大值）**

| 时间范围 | 条数 | 磁盘占用 |
|---------|------|---------|
| 1 天 | 23 万条 | ≈ **143 MB** |
| 1 个月 | 691 万条 | ≈ **4.2 GB** |
| 3 个月 | 2074 万条 | ≈ **12.6 GB** |

**叠加死区过滤（设备数据无变化不存）**

工业场景大量点位变化不频繁，实际写入量为理论值的 30%-70%：

| 死区过滤效果 | 3个月实际写入 | 3个月磁盘占用 |
|-------------|-------------|-------------|
| 保守（70% 写入） | 1452 万条 | ≈ **8.8 GB** |
| 中等（50% 写入） | 1037 万条 | ≈ **6.3 GB** |
| 乐观（30% 写入） | 622 万条 | ≈ **3.8 GB** |

> WiredTiger 存储引擎默认启用 snappy 压缩，实际磁盘占用还能再降 30%-50%。

**综合磁盘规划**

| 项目 | 磁盘占用 |
|------|---------|
| 3 个月热时序数据（含索引，中等死区效果） | ~6-10 GB |
| 业务数据（用户/设备/点表/报警规则/通知人） | ~0.5 GB |
| 实时数据（每设备最新值，80 条） | 可忽略 |
| 报警记录 + 操作日志 | ~0.5 GB |
| MongoDB 预分配 + oplog | ~2-3 GB |
| **MongoDB 合计** | **约 10-15 GB** |
| **建议配置云盘** | **100 GB 起步**（留足余量 + 未来设备扩容） |

### 4.4 冷热分层存储策略

```
┌─────────────────────────────────────────────────────┐
│                   热数据（近 3 个月）                  │
│              MongoDB，按月分集合存储                    │
│     point_history_202606 / 202607 / 202608         │
│              支持实时查询、范围检索                      │
└───────────────────────┬─────────────────────────────┘
                        │ 每月 1 号定时任务
                        │ 导出 3 个月前的整月集合
                        ▼
┌─────────────────────────────────────────────────────┐
│                  冷数据（超 3 个月）                   │
│              OSS 对象存储，快照归档                     │
│    iot-history/{year}/{month}/point_history_*.json.gz│
│              压缩存储，低频回查下载                      │
└─────────────────────────────────────────────────────┘
```

**热数据（MongoDB）**：
- 保留近 3 个月设备历史数据，支持实时查询
- 存储模型：按设备存原始数据包，每台设备 30 秒一条记录，记录含 500 字节 BinData 原始包
- 可按月分集合（`device_history_YYYYMM`），也可单集合存储（3个月仅2000多万条，单集合无压力）
- 复合索引：`(deviceId, timestamp)`，提升按设备+时间范围的查询效率
- 死区过滤：设备数据无变化时不新增记录，减少 30%-70% 写入量

**冷数据（OSS 归档）**：
- 超过 3 个月的历史数据，由定时任务自动归档至 OSS
- 归档格式：BSON / JSON 压缩包（gzip），文件名含月份标识
- OSS 目录结构：`iot-history/{year}/{month}/device_history_YYYYMM.json.gz`
- 归档完成后从 MongoDB 删除对应月份集合，释放存储空间
- 超 3 个月数据查询：从 OSS 下载对应月份快照，本地解析原始包回查（低频操作）

### 4.5 点位数据解析方式

历史数据查询时，点位值不直接存储在数据库中，而是由应用层从 500 字节原始数据包中按指针偏移量解析：

1. 查询设备历史记录列表（含 rawData 原始包）
2. 读取该设备的点表配置，获取每个点位的寄存器类型、地址偏移、位偏移、数据类型、转换公式
3. 应用层按点表配置从 rawData 中解析出各点位的原始值
4. 执行正向公式转换，得到展示值
5. 返回给前端

**优势**：点位解析规则变更（新增点位、修改公式）不影响历史数据，无需数据迁移。

### 4.6 定时归档任务

| 项 | 说明 |
|----|------|
| 执行频率 | 每月 1 号凌晨（低峰期） |
| 任务内容 | 导出 3 个月前的整月集合 → 压缩 → 上传 OSS → 校验 → 删除 Mongo 集合 |
| 可靠性 | 上传 OSS 成功并校验文件大小后再删除 Mongo 数据，避免数据丢失 |
| 归档记录 | 每次归档写入归档日志（月份、条数、文件大小、OSS 路径、执行时间、状态） |
| 双实例 | 仅一个实例执行（通过分布式锁或 MongoDB 原子操作抢占），避免双实例重复归档 |

### 4.7 存储分类总览

| 数据类型 | 存储 | 保留策略 | 说明 |
|---------|------|---------|------|
| 业务数据 | MongoDB 集合 | 永久 | 用户、设备、点表、报警规则、通知人 |
| 设备实时数据 | MongoDB 集合 | 永久（仅最新值） | 每设备最新一条记录（含原始包），更新而非追加 |
| 设备历史数据（热） | MongoDB 集合 | 3 个月 | 按设备存原始数据包，30秒一条，死区过滤，(deviceId, timestamp) 索引 |
| 设备历史数据（冷） | OSS 对象存储 | 按需（长期） | 超 3 个月快照 gzip 压缩归档，低频回查 |
| 报警记录 | MongoDB 集合 | 永久或按策略 | 报警发生 + 恢复事件，数据量小 |
| 操作日志 | MongoDB 集合 | 按策略归档 | 点位控制操作记录（操作人、时间、点位、下发值） |
| 归档日志 | MongoDB 集合 | 永久 | 记录每次冷数据归档任务执行情况 |

### 4.8 存储优化策略

- **按设备存原始包**：不按点位拆分，一条记录包含设备全部 80 个点位数据，写入量降低 1-2 个数量级
- **死区过滤**：设备数据无变化时不写入历史，可减少 30%-70% 写入量
- **复合索引**：`(deviceId, timestamp)`，覆盖按设备+时间范围查询场景
- **实时与历史分离**：实时数据集合（仅最新值）与历史数据集合分开存储
- **应用层解析点位**：点位值从原始包按指针解析，不单独存储，节省空间且灵活
- **压缩归档**：冷数据 gzip 压缩后存 OSS，存储成本约为原始数据的 10%-20%
- **WiredTiger 压缩**：MongoDB 默认 snappy 压缩，磁盘占用再降 30%-50%

## 5. 多租户隔离

- 登录时获取用户关联的租户 ID（一个用户可关联多个租户）
- 所有业务数据按租户 ID 隔离，查询时自动过滤当前租户范围
- 设备、点表、报警规则、通知人均归属特定租户
- 管理员可管理本租户全部资源，操作人员仅可操作本租户授权设备

## 6. 认证与权限

### 6.1 认证方式

- JWT 无状态认证，账号密码登录
- 登录成功后返回 JWT Token，前端存储于 localStorage / Cookie
- 后续请求 Header 携带 `Authorization: Bearer <token>`
- JWT 密钥通过环境变量注入，不硬编码
- Token 设置过期时间，支持刷新机制

### 6.2 角色权限

| 角色 | 权限范围 |
|------|---------|
| ADMIN（管理员） | 全部功能权限：设备管理、点表管理、点位控制、通知人管理、报警管理 |
| OPERATOR（操作人员） | 仅查看类 + 点位控制：设备查看、点表查看、点位监控、可写点位控制、报警查看、通知人查看 |

**权限实现**：
- Spring Security 注解 `@PreAuthorize` 控制接口级权限
- 业务层二次校验（如点位控制时校验点位读写权限，只读点位拦截）
- 前端按角色动态渲染菜单与操作按钮（后端校验为准，前端仅做体验优化）

## 7. 采集方式

- **仅 MQTT**：设备与平台统一使用 MQTT 协议通信
- 设备侧：工业网关 / PLC 直连 EMQX Broker，上报采集数据
- 平台侧：SpringBoot 作为 MQTT 客户端订阅设备上报 Topic，发布控制指令 Topic
- 双实例通过 MQTT 共享订阅（`$share/group/topic`）实现消费负载均衡与去重
