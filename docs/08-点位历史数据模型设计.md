# 08 - 点位历史数据模型设计(变化点存储 + 阶梯图)

> **文档目的**:前后端共用的数据契约。前端画图表、后端做存储/查询,均以本文档为准,无需重复设计沟通。
>
> **状态**:设计定稿,代码改造清单见文末。

---

## 1. 背景与问题

系统上报链路做了**死区过滤**(值不变不落库),导致:一个点位一整天都是 10,历史表里只有 1 条数据,前端画图无法呈现"整段时间都是 10"的水平线。

问题本质:**"变化事件"存储** 与 **"任意时刻的值"展示** 是两种不同的数据形态,中间需要一个约定的转换规则。本文档定义这个规则。

---

## 2. 核心设计(三句话)

1. **只存变化点**:值不变,不写新行。"结束时间"不存,由下一行(或"现在")隐式给出。
2. **一行 = 一个点位的一个值**:每行记录某点位在某个时刻的值,不含其他点位信息。
3. **查询时补区间端点**:历史查询 API 自动在区间首尾补"最后已知值",前端画阶梯图即得完整曲线。

---

## 3. 存储模型

### 3.1 历史表 `point_history`(行展开,核心)

| 列 | 类型 | 说明 |
|---|---|---|
| id | varchar | 雪花 ID |
| device_id | varchar | 设备 ID |
| device_code | varchar | 设备编码(冗余,便于排查) |
| **point_code** | varchar | 点位编码(如 `temperature`) |
| **ts** | timestamptz | 该值**生效的起始时刻** |
| **value** | varchar | 原始值(字符串存储,展示层按点表公式转换) |
| tenant_id | varchar | 租户 |
| state / created_at / ... | — | BaseEntity 审计字段 |

**索引**:`(device_id, point_code, ts)` —— 单曲线查询的主路径。

**行语义**:该点位从 `ts` 时刻起值为 `value`,保持到该点位下一行为出现为止;若再无新行,保持到"现在"。

### 3.2 实时表 `point_realtime`(快照,辅助)

| 列 | 类型 | 说明 |
|---|---|---|
| device_id | varchar(唯一) | 设备 ID |
| **points** | jsonb | 最新整套快照 `{"temperature":"2", ...}` |
| timestamp | timestamptz | 最近一次上报时刻 |

分工:**realtime 管"当前值"**(最新快照整存整取),**history 管"任意时刻的值"**(变化点逐点位落行)。两表独立,互不参与对方的查询路径。

### 3.3 为什么不存区间(开始时间 + 结束时间)

| 问题 | 说明 |
|---|---|
| 写入要回头改 | 插入时不知道结束时间,必须等下次变化回头 update,时序大表频繁回写性能差 |
| 永远有一条未闭合数据 | 最新一条的 end 永远为空,宕机残留未闭合记录,查询逻辑复杂化 |
| 违背时序惯例 | 时序表(InfluxDB / TimescaleDB / 工业组态)均为只追加、不可变(append-only),利于写入、压缩与按时间淘汰 |
| 查询更复杂 | 区间重叠判断难以用派生查询表达(项目约定:Repository 不写 SQL) |

## 4. 写入规则(死区过滤,按点位)

设备一次上报携带多个点位 `values: {code: value}`,处理规则:

| 步骤 | 规则 |
|---|---|
| 1 | 逐点位与实时快照中的旧值比较 |
| 2 | **有变化**(或首次上报、实时表中无旧值)→ 为该点位写 1 行 history |
| 3 | 无变化的点位 → 不写任何行 |
| 4 | 全部点位处理完后,更新 realtime 快照与上报时间戳(无论是否有变化) |

示例:上报 20 个点位,只有 2 个变化 → 仅写 2 行。

> 对比快照模型(一次变化写 1 行大 JSON):行展开模型下,未变化的点位**永不**重复存储,单点位查询无需投影,存储与查询双优。

## 5. 查询 API 契约(前端对接处)

### 5.1 接口

```
GET /devices/{deviceId}/history?pointCode=temperature&from=...&to=...&limit=500
```

| 参数 | 必填 | 说明 |
|---|---|---|
| deviceId | 是 | 路径参数 |
| **pointCode** | **是** | 单个点位编码(单曲线场景;多曲线 = 多次并行请求) |
| from / to | 是 | 查询区间,ISO-8601(Instant) |
| limit | 否 | 默认 500,上限 5000(变化点条数,补点不占用) |

**响应**:一行的数据结构,**一行只代表一个点位当时的一个值**:

```json
[
  { "timestamp": "2026-08-28T09:00:00Z", "pointCode": "temperature",
    "pointName": "温度", "rawValue": "2", "displayValue": 2.0, "unit": "℃" },
  { "timestamp": "2026-08-28T20:00:00Z", "pointCode": "temperature",
    "pointName": "温度", "rawValue": "3", "displayValue": 3.0, "unit": "℃" }
]
```

| 字段 | 说明 |
|---|---|
| timestamp | 值生效的起始时刻(ISO-8601) |
| pointCode / pointName | 点位编码 / 点表名称 |
| rawValue | 原始上报值(字符串) |
| displayValue | 经点表正向公式转换后的展示值(转换失败时等于 rawValue) |
| unit | 单位(点表定义,可为 null) |

**排序**:timestamp 升序。

### 5.2 补点规则(后端实现规范)

```
① 补首点:查 from 之前(≤)该点位最后 1 行
    → 有 且 其 ts ≠ from      → 补 {from, 该值}
    → 该点位从未上报过        → 无首点
② 变化点:[from, to] 内真实数据升序返回(受 limit 截断)
③ 补尾点:仅当 ② 未被 limit 截断 且 最后 1 行 ts < to
    → 补 {to, 最后已知值}
④ ② 为空 且 ① 有值          → 返回首尾 2 行(同值),水平线成立
⑤ ② 为空 且 ① 无值          → 返回空数组(区间内确实无数据,前端显示"暂无数据")
```

### 5.3 边界情况速查

| 场景 | 返回 |
|---|---|
| 区间早于首次上报 | `[]`(⑤) |
| 全天无变化,只有 1 行真实数据 | 首行真实 + 尾行补点,2 行 |
| 最后一次变化恰在 to 时刻 | 不重复补尾点 |
| 首次上报恰在 from 时刻 | 首行即真实数据,不重复补首点 |
| 变化点超过 limit | 返回前 limit 行,**不补尾点**(数据被截断,尾点值不可知) |
| displayValue 公式计算失败 | 回落为 rawValue,接口不报错 |

## 6. 前端图表约定

### 6.1 图表类型

**阶梯图(step line)**。ECharts 配置:

```js
series: [{
  type: 'line',
  step: 'end'   // 关键:每个点的值从该时刻延续到下一个点
}]
```

### 6.2 数据点语义

`(timestamp, value)` = **"该时刻起值为 value,保持到下一时刻"**。前端**不需要**自己做插值/填充,后端已补齐区间端点,直接把返回数组喂给 ECharts 即可画出完整水平线段。

### 6.3 多点位多曲线

对每个 pointCode 各发一次请求(可并行),一个 series 一个点位。

### 6.4 时间轴

timestamp 为 UTC(Instant),前端按本地时区展示;补出的首尾点自然对齐查询边界,曲线铺满整个 x 轴区间。

## 7. 场景演示

### 场景 A:正常变化(单点位 temperature)

时间线:08:00 值变 2 → 09:30 变 5 → 之后保持 → 20:00 变 3 → 23:00 又上报 3(不变,丢弃)。

**库里 3 行:**

| ts | point_code | value |
|---|---|---|
| 08:00 | temperature | 2 |
| 09:30 | temperature | 5 |
| 20:00 | temperature | 3 |

**查询 [09:00, 21:00] 返回 4 行:**

| timestamp | value | 来源 |
|---|---|---|
| 09:00 | 2 | ①补首点(08:00 的值) |
| 09:30 | 5 | ②真实 |
| 20:00 | 3 | ②真实 |
| 21:00 | 3 | ③补尾点 |

```
5        ┌──────┐
2 ───────┘      │
                └──────── 3
 09:00   09:30   20:00   21:00
```

### 场景 B:一整天都是 10

08:00 上报 10,之后 24 小时无变化。**库里 1 行**:

| ts | point_code | value |
|---|---|---|
| 08:00 | temperature | 10 |

**查询 [00:00, 24:00] 返回 2 行:**

| timestamp | value | 来源 |
|---|---|---|
| 08:00 | 10 | ②真实 |
| 24:00 | 10 | ③补尾点 |

```
10 ━━━━━━━━━━━━━━━━━━━━
   08:00              24:00
```

一行数据,一条完整水平线。

### 场景 C:查询区间早于首次上报

设备 08:00 才上线,查 [00:00, 06:00] → `[]`,前端显示"暂无数据"(诚实,不猜值)。

## 8. FAQ

**Q1:为什么不前端拿到变化点自己补?**
补点依赖"from 之前的最后已知值",前端要多发一次请求且逻辑分散;后端一次返回完整序列,契约最简单。

**Q2:报表需要"1~8 点值 2"这样的区间列表怎么办?**
查询时的内存转换(相邻行两两配对),不改存储。存储永远 append-only。

**Q3:同一时刻多点位变化,是几行?**
几个点位变化就几行,同一 ts 不同 point_code,各自独立构成各自的时间线。

**Q4:补点行的 displayValue 用哪次公式转换?**
补点行与其他行一致,按该行 rawValue + 当前点表公式转换。点表公式修改只影响之后的展示,不影响已存的 rawValue。

**Q5:limit 截断时为什么不补尾点?**
截断后"最后已知值"已不是 to 时刻的真实值,补了会误导。前端可用 realtime 接口的当前值兜底展示"至今"。
